# NOCScheduler Toolchain & Repository Conventions

> Phase: WP-F00 — Repository & Toolchain Bootstrap  
> Package manager: npm  
> Runtime policy: Node.js 22.x  
> Source language: TypeScript / TSX strict mode

## 1. Runtime policy

NOCScheduler targets Node.js 22 for the project runtime baseline so local development aligns with the Firebase-managed Node runtime selected by the architecture. The root `.nvmrc` and `package.json#engines` express this policy.

Java 21 is the forward-compatible local prerequisite for the Firestore Emulator work introduced later. WP-F00 itself does not require the emulator to run.

## 2. Package manager and lockfile

Canonical package manager: **npm**.

- npm workspaces are configured in the root `package.json`.
- `package-lock.json` must be generated by npm and committed.
- pnpm/yarn lockfiles are not allowed in the normal workflow.
- Dependency upgrades must be intentional and must update the lockfile.

## 3. Workspace naming convention

WP-F01 will populate the reserved workspace topology. Canonical package identities should follow:

```text
apps/web              → @nocscheduler/web
apps/api              → @nocscheduler/api
packages/domain       → @nocscheduler/domain
packages/contracts    → @nocscheduler/contracts
packages/ui           → @nocscheduler/ui
```

Rules:

- application workspaces may depend on shared packages;
- shared packages must not import application-private modules;
- domain code must not depend on React or Tailwind;
- contracts must not import browser-only code;
- avoid deep cross-workspace relative imports.

## 4. Import alias convention

When WP-F01 creates application workspaces:

- `@/` may be used as the application-local source alias inside an app;
- cross-workspace imports use the npm workspace package name, for example `@nocscheduler/domain`;
- do not create multiple aliases for the same boundary;
- aliases must be represented consistently in TypeScript, Vite/build tooling, tests, and editor resolution.

## 5. TypeScript baseline

The root baseline enforces:

- `strict: true`;
- `noUncheckedIndexedAccess: true`;
- `exactOptionalPropertyTypes: true`;
- `noImplicitOverride: true`;
- `useUnknownInCatchVariables: true`;
- `forceConsistentCasingInFileNames: true`;
- no emit during type verification.

Workspace-specific configs may extend the root base and add browser/Node module settings appropriate to that workspace. They must not weaken critical strictness merely to silence errors.

## 6. Source extension policy

- React/JSX: `.tsx`
- Standard first-party modules: `.ts`
- Temporary generator and repository tooling may use `.cjs` where CommonJS execution is intentional.
- Tool configuration may use `.mjs` when that is the tool-native ESM format.
- First-party application code under `apps/` and `packages/` must not drift to `.js`/`.jsx`.

## 7. Foundation quality gates

WP-F00 provides these runnable gates:

```text
npm run check:runtime
npm run typecheck
npm run lint
npm run format:check
npm run check:repo
```

WP-F02 later expands quality infrastructure with unit tests, browser tests, accessibility checks, integration suites, dead-code checks, and CI orchestration.

## 8. Environment and secrets

- Real environment files stay local and ignored.
- `.env.example` contains only safe documentation/placeholders.
- Never commit service-account JSON or private keys.
- Firebase credentials and project configuration are introduced only in their appropriate phase.

## 9. Line endings and formatting

Repository text uses UTF-8 and LF line endings. EditorConfig establishes common whitespace rules. Prettier is the canonical formatter for supported source/config files; broader formatting scope can be added as implementation grows.
